機能設計書

qftp-client(ネイティブクライアント)

作成日: 2026-09-03 更新日: 2026-09-03

概要

機能名

qftp-client: REPL と one-shot サブコマンドを持つネイティブクライアント。ライブラリ qftp-client-core と CLI バイナリ qftp-client の 2 クレート。

目的

scp / sftp と同じ感覚で使え、再開・整合性検証・圧縮・0-RTT が自動で効くクライアントを提供します。プロトタイプの機能を、Session API・一貫したサーバ信頼ポリシー・統一された終了コード規約のうえに再構成します。

想定ユーザー

対話利用者(REPL)、スクリプト利用者(one-shot、batch)、ライブラリ利用者(sync / watch / テストキット)。

利用シーン

  1. qftp-client work でエイリアス接続し、ls / get -r / put を対話実行。
  2. qftp-client put ./dump.tar.gz qftp://files.example/backups/ をバックアップスクリプトから実行し、終了コードで判定。
  3. CI から --batch で標準入力のコマンド列を実行。

スコープ

含むもの

  • Session API: connect / request / get / put / close、再開判定、StalePartial 再試行、圧縮フォールバック。
  • サーバ信頼ポリシー: CA / システムルート / TOFU / insecure を 全経路で同一に適用。
  • 設定ファイル([defaults] + [host.*])、known_hosts、セッションチケット、履歴。
  • REPL(クォート対応パーサ、補完、進捗)、one-shot(put / get / ls / stat / rm / mkdir / rmdir / rename)。
  • 拡張区分: get -r / put -r / mget(REPL と one-shot の両方)、双方向 --bwlimit。
  • 同期区分: sync / watch。

含まないもの

  • put-multi(作らない。sync の複数ターゲット指定で代替、ADR-010)。
  • sync --checksum(作らない、ADR-010)。
  • リモート補完。
  • Windows(非 Unix は起動時エラー、ADR-011)。

前提条件

  • サーバは qftp/1 準拠。
  • 転送のクライアント側状態機械は qftp-core が提供。

機能要件

主要フロー

  1. 引数解析 → 設定解決(組込既定 < [defaults] < [host.alias] < URL < フラグ)。
  2. Session::connect(spec, trust, options): 名前解決 → 各アドレスに順次接続(最後以外は 8 s 予算)→ チケットがあれば 0-RTT 再開 → ハンドシェイク → 信頼検査(CA モードならホスト名、TOFU なら pin) → 検査前にアプリケーションデータを送らない → mTLS があれば identity は サーバ側で解決。
  3. 初期パスがあれば Cd。
  4. REPL / one-shot / batch がコマンドを Session に発行。要求は逐次(1 本ずつ)。
  5. 終了時に Quit を送り、チケットを保存(insecure / TOFU では保存しない)。

入力

起動形態: qftp-client [FLAGS] [TARGET](REPL / -e / --batch)と qftp-client [FLAGS] <SUBCOMMAND>(one-shot)。TARGET は qftp://[user@]host[:port][/path] またはエイリアス。パスワード付き URL は拒否。

フラグ・サブコマンド・REPL コマンド: 完全な一覧と構文は CLI リファレンス §3〜§5 が正本です。要点は、サーバ信頼(--ca / -T / --insecure)、mTLS、0-RTT、帯域制限、圧縮、--json、batch 制御(--fail-fast)の各フラグと、ls / cd / get / put / mget / mkdir / rmdir / rm / rename / chmod / stat / quota / ローカル操作 / ! / stats / quit の REPL コマンドです。

設定ファイル: ~/.qftp/config.toml の [defaults](compress / bwlimit / tofu / zero_rtt / パス類 / fail_fast)と [host.*](endpoint と明示キー、プロトタイプ互換 + tofu / compress / bwlimit)。キー一覧と優先順位は 設定リファレンス §3 を参照。

出力

結果は stdout、診断・進捗は stderr(進捗バーは TTY のみ)。--json は one-shot の結果を 1 行 JSON で出す。終了コードは sysexits(0 / 64 / 65 / 69 / 70 / 74 / 77)を全経路で守り、batch / -e は --fail-fast 既定で最初の失敗で止まる。出力形式・JSON スキーマ・ErrorCode と終了コードの対応表は CLI リファレンス §6 が正本です。

ビジネスルール

信頼モードチェーンホスト名ピン0-RTTチケット保存
既定 / --ca検証SAN(RFC 6125 相当)、SAN なしなら CNなし有効あり
TOFUなしなしleaf SHA-256 を known_hosts に照合。初回は対話なら y/n 確認、非対話なら拒否(--tofu-accept-new で自動受理)無効なし
insecureなしなしなし無効なし
  • 信頼検査に失敗した接続はアプリケーションデータを 1 バイトも送らずに閉じる。
  • get: 既存ローカルの regular file があれば自動再開(--force で 0 から)、トレーラ不一致でローカル削除、InvalidRange 再開失敗は 0 から 1 回再試行。size + offset == total_size を検査。
  • put: <remote>.qftp.partial を Stat して再開、圧縮は ≥ 1024 バイトかつ非既圧縮拡張子、checksum_trailer=true、Unsupported(zstd)なら Identity で再送、ChecksumMismatch|InvalidRange(再開時)は 0 から 1 回再試行。Put ヘッダ送出後は待たずに本体を流し、同じストリームの応答を並行して読む。Err を受けたら送信を止めてストリームを reset する(ADR-009)。
  • ls / mget / get -r / sync は next_cursor を必ず追う。
  • 再帰 get: BFS、上限 10,000 ディレクトリ、エントリ名は安全名検査、既存ローカル名は再開判定に回す(スキップしない)。再帰 put: symlink はスキップし件数を報告。
  • 上書き規則(one-shot): -n > -f > (-i または TTY → 確認) > 上書き。REPL も同じ規則(既定は確認)。
  • 0-RTT: 再開ハンドシェイクのみ行い、early data にアプリケーションデータは載せない(プロトタイプ互換。サーバの許可リストは将来の最適化余地)。

異常系・例外処理

  • URL 不正 / 未知エイリアス: 64。エイリアス一覧を提示。
  • 接続不能(全アドレス失敗): 69。
  • TOFU 不一致: SSH 風バナーを stderr に出し 77。known_hosts のパスは実際に使ったものを表示。
  • 転送中の Ctrl-C: 現在のストリームを reset し、Quit を送って終了(partial はサーバ・ローカルとも残す)。
  • サーバの RateLimited: RetryAfter に従い 1 回再試行。
  • 接続断(アイドル・サーバ終了): 65 で終了。REPL は再接続を提案しない(明示的に再起動)。

非機能要件

性能

  • アップロードは 1 MiB チャンク、ダウンロードは 256 KiB。
  • --bwlimit は上下双方向、トークンバケット(1 s バースト)。
  • 進捗バーは 120 ms 更新。

セキュリティ

  • known_hosts / チケット / 履歴は 0600。チケットは V2 形式(フィンガープリント埋め込み、24 h TTL)。
  • ローカルファイルは O_NOFOLLOW で開く。リモートから受けたエントリ名は安全名検査(/ \\ NUL . .. 拒否)と端末エスケープ除去を通す。
  • パスワードは扱わない(URL のパスワードは拒否)。

リスク・代替案

リスク

  • quiche ではハンドシェイク前に pin を検査できないため、「検査前にデータを送らない」規律に依存する。Session API の型で「未検証接続」と「検証済み接続」を分けて強制する。
  • Put の早期 Err は本体の一部を送った後に届き得る。送信済みバイトは無駄になるが正しさには影響しない。送信ループは受信側を毎ティック確認する。

代替案と棄却理由

  • REPL ロジックをバイナリに残す(プロトタイプ形式): テスト不能で重複が増えるため不採用。
  • 0-RTT で Cd / Stat を early data に載せる: 1 往復の節約になるが、再送・拒否処理が増える。コア区分 後の最適化候補。
