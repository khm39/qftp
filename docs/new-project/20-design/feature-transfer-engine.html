転送エンジン(Get / Put、sans-I/O)

作成日: 2026-09-03 更新日: 2026-09-03

概要

機能名

転送エンジン。Get / Put のサーバ側状態機械と、対称なクライアント側状態機械を、ソケット・ディスクに依存しない形で提供する qftp-core::transfer モジュール。

目的

プロトタイプでは転送の状態が共有クレートに、遷移がサーバクレートに分かれ、ブリッジは別実装を持っていました。本機能は転送ロジックを 1 箇所に集約し、quiche のイベントループ、tokio ベースのブリッジ、純メモリのテストが同一コードを駆動できるようにします。

想定ユーザー

直接の利用者は qftp-server、qftp-web-bridge、qftp-client-core の実装者。エンドユーザからは見えません。

利用シーン

  1. サーバが Get 要求を受け、ファイルを読みながら本体とトレーラを送る(再開・圧縮あり)。
  2. サーバが Put 要求を受け、temp に書きながらチェックサムを検証し、原子的に rename する(再開・圧縮あり)。
  3. クライアントが同じ状態機械の鏡像で、ローカルファイルと QUIC ストリームを仲介する。

スコープ

含むもの

  • GetServer / PutServer / GetClient / PutClient の 4 状態機械。
  • イベント(バイト到着、FIN、I/O 完了、送信余地)とコマンド(ファイル読み書き、送信、応答、コミット、中断)の型定義。
  • プレフィクス再ハッシュ、zstd の単一フレーム符号化 / 復号、トレーラ分離、伸長爆弾ガード、クォータ予約の会計規則。
  • 失敗時の後始末規則(temp の扱い、予約解放、使用量計上)の一元化。

含まないもの

  • QUIC ストリームの実 I/O、ファイルの実 I/O(ホストの責務)。
  • ACL、レート制限、0-RTT ゲート(要求受付側の責務。エンジンは検査済みの要求を受け取る)。
  • パス解決(qftp-core::path が行い、エンジンは解決済みパスを受け取る)。

前提条件

  • ワイヤ仕様 qftp-protocol.md の Get / Put 節と wire-format.md の Body streaming 節が正本。
  • ホストは「1 ストリーム = 1 転送」を保証し、FIN をイベントとして通知できる。
  • ホストはファイル操作を非同期(完了通知つき)で実行できる。同期で実行しても正しく動く(完了イベントを即時に投入する)。

機能要件

主要フロー

サーバ Get

  1. GetServer::start(req, opened_file_meta): ファイルが regular か、サイズ上限、offset ≤ len、圧縮可否を判定し、Cmd::Respond(FileReady) を返す。
  2. offset > 0 なら Cmd::ReadFile{0..offset} をチャンク単位で発行し、Event::ReadDone でハッシュに畳む(ワイヤには何も出さない)。
  3. 本体: Cmd::ReadFile{pos, len} → Event::ReadDone(bytes) → ハッシュ更新 → (Zstd なら符号化) → Cmd::Send(bytes, fin=false)。送信余地は Event::SendCapacity(n) で通知され、エンジンは余地を超えて Send を発行しない。
  4. 本体完了後、Cmd::Send(trailer, fin=true)。

サーバ Put

  1. PutServer::start(req, temp_meta): 検証必須形(再開・圧縮)のチェックサム有無、size == plaintext_size、サイズ上限、再開時の temp 長一致、クォータ予約を判定し、失敗なら Cmd::Respond(Err) + Cmd::Abort。
  2. 再開時は Cmd::ReadFile{0..offset} でプレフィクスをハッシュ。到着済み本体は内部バッファに保留。
  3. Event::Bytes(chunk) ごとに本体 / トレーラ / 超過を分類し、本体は(Zstd なら復号後)Cmd::WriteFile(bytes)、トレーラは蓄積。
  4. Event::Fin で不足があれば UploadTruncated。トレーラ完備なら優先、なければヘッダ checksum、どちらもなければ未検証(fresh Identity のみ)。
  5. 検証成功で Cmd::Commit{temp, final, mode}、ホストの Event::CommitDone を待って Cmd::Respond(Ok)。

入力

イベント意味
Event::Bytes(Bytes)ストリームから受信した本体 / トレーラのバイト列
Event::Finピアが FIN を送った
Event::SendCapacity(usize)送信可能バイト数の更新(流量制御・輻輳制御の反映)
Event::ReadDone{id, bytes} / Event::ReadFailed{id, err}ファイル読み取り完了 / 失敗
Event::WriteDone{id} / Event::WriteFailed{id, err}ファイル書き込み完了 / 失敗(ディスクフルを含む)
Event::CommitDone / Event::CommitFailed(err)rename + mode 適用の結果
Event::Cancel接続断・シャットダウンによる中断

出力

コマンド意味
Cmd::Respond(Response)制御フレームを送る(FileReady / Ok / Err)
Cmd::Send{bytes, fin}本体またはトレーラを送る。fin は最後のバイトに立てる
Cmd::ResetStream(code)本体送出後に失敗した Get の通知(実装定義のエラーコード)
Cmd::ReadFile{id, pos, len} / Cmd::WriteFile{id, bytes}ファイル I/O 要求(ホストがワーカーで実行)
Cmd::Commit{temp, final, mode}原子的 rename と mode 適用
Cmd::Abort{keep_partial: bool}後始末。keep_partial=true は再開用に temp を残す
Cmd::Account(AccountingDelta)クォータ会計(予約解放、使用量加算)。ホストが User に反映

ビジネスルール

  • トレーラは常に [0, offset + body長) の平文累積 BLAKE3。トレーラ長は HashAlgorithm::digest_len() が唯一の情報源(32 固定バッファを持たない)。
  • Zstd は転送ごとに 1 フレーム、window_log = 23 を符号化側で強制、復号側で上限設定。復号出力は min(plaintext_size, MAX_FILE_SIZE) で打ち切り、超過は UploadOverflow、不正フレームは DecodeError。
  • 圧縮判定(サーバ Get / クライアント Put 共通): サイズ ≥ 1024 バイト、かつ既圧縮拡張子一覧に該当しない、かつピアが受理可能。
  • Put の temp 名は TempName::for_final(path) の 1 箇所で決め、<name>.qftp.partial。Ls 非表示・Rm / Rename / Get の対象外・掃除対象の判定はすべて TempName::is_temp を使う。
  • 失敗時の後始末は経路に依存せず次の表に従う。
失敗temp会計応答
受付検証失敗(開始前)fresh なら削除、再開なら残す予約なしErr
UploadTruncated / 接続断残す(再開用)書けた分を使用量に計上、予約解放Err(送れる場合)
UploadOverflow / DecodeError / ChecksumMismatch / Malformed削除再開プレフィクス分を返金、予約解放Err
書き込み失敗(ディスクフル等)残す書けた分を計上Internal
Commit 失敗残す書けた分を計上Internal

異常系・例外処理

  • Get で offset > len: InvalidRange + ErrorDetails::Range。
  • 再開 Get 中にファイルが縮小(ReadDone が短い): 本体送出前なら InvalidRange、送出後なら ResetStream。
  • Put 再開で temp 長が offset と不一致: InvalidRange + Range details。
  • 圧縮 Put で size != plaintext_size: Malformed。
  • 再開 / 圧縮 Put でチェックサムなし: Unsupported(本体を読む前に返す)。
  • 同一宛先への並行 Put: 受付側の UploadClaim が AlreadyExists を返す(エンジンは claim 済みで開始される)。
  • ホストが Event::Cancel を投入: エンジンは Cmd::Abort{keep_partial: true} と会計コマンドを返して終了。

非機能要件

性能

  • チャンクサイズ: 読み取り 256 KiB、受信処理 64 KiB(設定可能)。
  • エンジンは SendCapacity を超える Send を発行しない(ホストがバッファを抱えない)。
  • 同一スレッドで複数エンジンを回す前提で、1 イベント処理は O(チャンク長)。

セキュリティ

  • 伸長爆弾: 平文出力カウンタ + window 上限 + plaintext_size による事前拒否。plaintext_size をメモリ確保に使わない。
  • temp は owner-only(0600)・O_NOFOLLOW で開く(ホスト規約として機能設計書サーバに記載)。
  • エンジンはパスを解釈しない(解決済みパスのみ)。

可用性

N/A(ライブラリ。可用性はホストの設計に従う)

ロギング・監視

  • エンジンは tracing の span を転送単位に張り、状態遷移を debug、失敗を warn で出す。
  • 完了 / 失敗 / バイト数は Cmd::Account と最終結果でホストに返し、ホストがメトリクスに反映する(エンジンはメトリクス実装を知らない)。

影響範囲・連携

影響する既存機能

  • サーバのストリーム dispatch(エンジンのホスト実装)。
  • Web ブリッジ(tokio ホスト実装)。
  • クライアントコアの get / put(クライアント側状態機械のホスト)。

外部システム連携

N/A

データモデル変更

ディスク上の temp ファイル規則 <name>.qftp.partial(プロトタイプ互換)。DB なし。

リスク・代替案

リスク

  • イベント / コマンド境界の抽象が厚くなり、ホストごとのアダプタが複雑化する。
  • 送信余地の管理をエンジン側で誤ると、quiche の stream_send が部分受理した際に二重送信・欠落が起きる。ホストは「受理されたバイト数」を SendCapacity で正確に返す規約とする。

代替案と棄却理由

  • async fn で書く: ネイティブ側が同期ループのため不可。
  • トレイトオブジェクト(FileIo / StreamIo)をエンジンに注入する: 同期呼び出しになりイベントループをブロックするため不可。コマンド / イベント方式なら非同期完了を自然に扱える。
