機能設計書

qftp-server(ネイティブサーバ)

作成日: 2026-09-03 更新日: 2026-09-03

概要

機能名

qftp-server: QUIC 上で qftp/1 を提供するネイティブサーバ。

目的

FTP / SFTP の代替として、単一 UDP ポート・TLS 1.3 必須・再開可能転送を、単一の非特権プロセスで提供します。プロトタイプの機能を、設定ファイル・I/O ワーカープール・sans-I/O エンジンの上に再構成します。

想定ユーザー

サーバ運用者(設定・監視)、およびネイティブクライアント / ブリッジの実装者。

利用シーン

  1. 社内 LAN のファイル配布サーバ(自己署名 + TOFU)。
  2. インターネット公開のアップロード受け口(mTLS + users.toml + retry + レート制限)。
  3. バックアップ先(クォータつきユーザ、JSON ログ、Prometheus 監視)。

スコープ

含むもの

  • 全 13 リクエスト(Ls ページネーションを含む)。
  • TLS 3 モード(cert/key、一時自己署名、永続自己署名)、mTLS、users.toml、ACL、クォータ。
  • stateless retry、接続上限、per-IP レート制限(Initial 用と要求用を別バケット)、0-RTT identity gate。
  • I/O ワーカープール、graceful shutdown、metrics / healthz、text / JSON ログ。
  • 設定ファイル(TOML)+ フラグ上書き、--check-config。

含まないもの

  • WebTransport(別バイナリ)。
  • OS ユーザ分離(ADR-004)。
  • 実行時の管理ソケット(kick / reload)。将来課題として SIGHUP による users.toml 再読込のみ検討。
  • Windows。

前提条件

  • プロトコル仕様パッケージ 10-protocol/ が正本。
  • 転送エンジンとパスサンドボックスは qftp-core から提供される。
  • プロセスは専用非特権ユーザで起動される。

機能要件

主要フロー

  1. 起動: 設定読込(ファイル → フラグ上書き)→ 検証 → tracing 初期化 → root canonicalize → TLS 材料の読込 / 生成 → users.toml 読込(home 作成、24 h 超の temp 掃除、使用量プライミングを spawn_blocking で実施)→ UDP bind → シグナルハンドラ → メトリクス HTTP タスク → QUIC ドライバタスク(tokio current_thread)。
  2. 受付: Initial ごとに DCID 長検査 → Initial レートバケット → retry(必須なら)→ 接続スロット → SCID 導出 → quiche::accept。詳細は 接続確立シーケンス。
  3. 要求処理: ストリームごとに Request をデコード → 要求レートバケット → 0-RTT ゲート → ACL → パス解決(spawn_blocking)→ 種別で分岐。メタデータ操作はブロッキングプールで実行し応答。Get / Put は転送エンジンをホストする。
  4. 終了: シグナル → 新規 Initial 無視 → 全接続に close → 転送完了待ち(ハード期限)→ ランタイム停止 → 終了。

users.toml(プロトタイプ互換): [anonymous] 任意、[[users]] に name / home / permissions{read,write,delete,mkdir,rmdir,rename,chmod} / quota_bytes。検証規則: 未知キー拒否、.. を含む相対 home 拒否、root 外 home 拒否、home の重複・入れ子拒否、名前重複拒否、quota_bytes = 0 拒否。

出力

  • ワイヤ応答(仕様どおり)。
  • ログ(text / JSON)。接続 ID、ユーザ名、ストリーム ID、操作、結果、所要時間を構造化フィールドで出す。
  • メトリクス(運用設計書 §3 参照)。
  • 終了コード: 0 正常、1 設定 / 起動失敗、2 実行時致命エラー。

ビジネスルール

  • ACL: Ls / Stat / Get / Cd → read、Put → write、他は同名。Pwd / Quota / Quit は権限不要。未知 Request は拒否(fail-closed)。
  • identity: ハンドシェイク完了時に peer cert の SAN dNSName → rfc822 → URI → CN の順で候補を作り users に照合。不一致は close 0x101、複数一致は Ambiguous として拒否。anonymous への格下げはしない。
  • 0-RTT: 許可リストは Cd / Pwd / Stat / Quit。mTLS 必須または名前付きユーザありなら全 early data を拒否。拒否は Unsupported。
  • Ls ページネーション: 名前順ソート、1 ページの上限は 10,000 エントリまたは約 1 MiB。カーソルは base64(HMAC(seed, dir_id || last_name) || last_name) の opaque 文字列で、検証失敗は Malformed。
  • クォータ: 予約→検査の順(used + in_flight > quota で拒否)。Rm / Rename(上書き)で減算。
  • temp: <name>.qftp.partial。Ls 非表示、Get / Rm / Rename の対象外、起動時に 24 h 超を掃除。
  • レート制限: Initial 用と要求用の 2 バケット群、いずれも IPv4 /32・IPv6 /64 キー、最大 4,096 バケットの LRU。
  • half-open: 未確立 5 s で破棄。アイドル 30 s。
  • Quota 応答: file_count は起動時プライミング + Put / Rm の増減で保持する(0 固定にしない)。

異常系・例外処理

  • 設定不正: 起動失敗(終了コード 1)。--check-config は検証のみ。
  • 鍵ファイルの権限不正: 起動失敗。
  • 接続上限・レート超過: Initial は黙って破棄(メトリクス加算)。要求は RateLimited + RetryAfter。
  • ストリームの STOP_SENDING / reset: 当該接続に閉じ、プロセスは継続(プロトタイプの回帰テストを移植)。
  • ワーカーの panic: 当該ジョブを Internal にし、ワーカーは再起動。
  • ディスクフル: Put は Internal、temp は残す(再開可)。
  • ハード期限内に転送が終わらない: 強制終了し、partial は次回起動の掃除 / 再開に委ねる。

非機能要件

性能

  • 流量制御窓: ストリーム 16 MiB、接続 64 MiB(仕様の実装定義値を踏襲)。
  • GSO 送信(Linux)。
  • 大容量転送中の Ls 応答時間が単独時の 2 倍以内(HOL 解消の受け入れ条件)。

セキュリティ

security-model.md のハードニング項目をすべて満たす。加えて: 鍵ファイル権限検査、metrics の非 loopback 警告、ログにトークン・パス以外の秘密を出さない、O_NOFOLLOW / O_NONBLOCK でのファイル open、祖先 symlink 再検査を変更操作の直前に行う(TOCTOU 緩和)。

可用性

  • 単一プロセス。graceful shutdown とハード期限。
  • /healthz: 受付ループの直近ティックが 5 s 以内なら 200、シャットダウン中は 503。

ロギング・監視

  • メトリクス: プロトタイプの 15 個を引き継ぎ、qftp_io_queue_depth、qftp_transfer_duration_seconds(histogram)、qftp_ls_pages_total を追加。
  • ログ: 接続開始 / 終了(理由)、identity 解決、要求ごとの結果、転送完了(バイト数、所要時間、encoding)。

影響範囲・連携

影響する既存機能

  • 転送エンジン(ホスト実装)。
  • qftp-admin(users.toml スキーマ互換)。
  • Web ブリッジ(同じ root / users.toml を共有。クォータは別プロセスで独立する制約を運用設計書に記載)。

外部システム連携

Prometheus、ログ集約、systemd。

データモデル変更

ファイルシステムのみ。temp 規則はプロトタイプ互換。永続自己署名の保存先はプロトタイプ互換。

リスク・代替案

リスク

  • quiche の early data 受理と 1-RTT ゲートの組み合わせを新構造で再現できるか(Phase 0 spike)。
  • spawn_blocking の往復コストが小さな要求(Stat 等)で支配的にならないか。Phase 3 の e2e で計測し、必要なら小さなメタデータ操作はドライバタスク上で同期実行する。
  • GSO 送信を tokio の UdpSocket::try_io 経由で行う実装の検証(Phase 0 spike)。
  • Ls カーソルの HMAC seed がプロセス寿命のため、再起動をまたぐページングは失敗する(仕様上は許容: 「サーバは発行していないカーソルを拒否してよい」)。

代替案と棄却理由

  • tokio-quiche による非同期化(spike 次第)。
  • 複数イベントループ + SO_REUSEPORT: QUIC の CID ルーティングと相性が悪く不採用。
