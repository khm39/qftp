# 決定事項(ADR ログ)

新規プロジェクトの設計を縛る決定を記録します。各項目は「状況 → 決定 → 理由 → 帰結」の順です。プロトタイプ時代の決定は必要なものだけ引き継ぎ、番号を振り直しています。

## ADR-001 ネイティブサーバ / クライアントの QUIC スタックは quiche + mio

- **状況**: プロトタイプは quiche + mio(ネイティブ)と quinn + tokio(ブリッジ)の 2 系統を持っていた。新規プロジェクトの方針として quiche の採用が指定された。
- **決定**: ネイティブサーバとクライアントは quiche(BoringSSL)を使い、mio による単一スレッドのイベントループで駆動する。
- **理由**: 方針指定。加えて、Cloudflare エッジでの運用実績、依存グラフの小ささ、単一スレッドによる予測可能なスケジューリング。
- **帰結**: 転送処理を同期ループで扱うため、状態機械を明示的に書く必要がある(ADR-002 で純粋ロジック化)。ディスク I/O はループ外へ(ADR-005)。TOFU / ホスト名検証はハンドシェイク後に行うため、検証前にアプリケーションデータを送らない規律をクライアントコアで型により強制する。tokio-quiche の採用可否は Phase 0 の spike で判断し、採用する場合も ADR-002 のエンジンはそのまま使う。

## ADR-002 転送エンジンは sans-I/O の状態機械として 1 実装

- **状況**: プロトタイプは転送状態を共有クレートに、遷移をサーバに置き、ブリッジは別実装を持っていた。
- **決定**: Get / Put のサーバ側・クライアント側状態機械を `qftp-core::transfer` に置き、入力はイベント(バイト到着、FIN、I/O 完了、送信余地)、出力はコマンド(ファイル読み書き、送信、応答、コミット、中断、会計)とする。エンジンはソケットにもディスクにも触れない。
- **理由**: quiche ループ、tokio ブリッジ、純メモリのテストが同一コードを駆動できる。失敗時の後始末規則を 1 箇所に集約できる。
- **帰結**: ホストごとにアダプタ(イベント供給・コマンド実行)が必要。エンジン API は転送エンジン機能設計書で固定する。

## ADR-003 ワイヤ符号化は手書き codec

- **状況**: プロトタイプは bincode 1.x(unmaintained)で仕様と同一バイト列を得ていたが、`#[serde(default)]` が無効であるなど誤解を招く構造だった。
- **決定**: `qftp-wire` に手書きのエンコーダ / デコーダを実装し、適合性はゴールデンベクタで担保する。serde は JSON 表現と設定ファイルのみに使う。
- **理由**: 仕様が bincode を非規範と明記している。末尾フィールド欠落の寛容デコードを残りバイト長で自然に実装できる。
- **帰結**: 約 500 行の codec と、ベクタに無い組合せを補う往復テスト・fuzz が必要。

## ADR-004 OS ユーザ分離は行わない(仮想ユーザモデル)

- **状況**: プロトタイプで setuid ワーカー方式を実装したのち却下した。
- **決定**: 単一の非特権プロセスで動作し、ユーザ単位の home と ACL はユーザ空間で強制する。
- **理由**: root 相当コンポーネントの追加はセキュリティ改善として割に合わない。qftp は OS アカウントを要求しない FTP 仮想ユーザモデルを志向する。
- **帰結**: カーネル DAC による多層防御はない。運用者は専用ユーザで起動し、root を限定する。

## ADR-005 ディスク I/O は I/O ワーカープールに委譲

- **状況**: プロトタイプは Get / Put のファイル読み書きをイベントループ上で行い、遅いディスクが全接続を止めた。
- **決定**: ファイルの open / read / write / rename / メタデータ操作はワーカースレッドプールで実行し、完了をチャネル + `mio::Waker` でループに通知する。ループはソケットと状態遷移だけを扱う。
- **理由**: HOL の解消。ADR-002 のコマンド / イベント方式と自然に整合する。
- **帰結**: スレッド間往復のコスト。小さな要求では無視できる範囲と見込むが、Phase 3 の e2e で計測する。

## ADR-006 Web ブリッジは別プロセス、トランスポートは Phase 7 開始時に決定

- **状況**: WebTransport は HTTP/3 の拡張 CONNECT を要し、quiche の h3 実装で賄えるか未確認。
- **決定**: ブリッジは別バイナリとして `qftp-core` のエンジンを tokio ホストで駆動する。トランスポートは (a) wtransport(quinn)を quiche 方針の明示的例外として使う、(b) quiche-h3 で実装する、のいずれかを Phase 7 開始時の調査で決める。
- **理由**: ネイティブ側の設計をブリッジの都合で歪めない。エンジン共有により、どちらを選んでも機能差は生じない。
- **帰結**: (a) の場合、ワークスペースに 2 スタックが残る(MSRV 差は許容範囲か再評価)。

## 引き継がない決定

- プロトタイプの「ブリッジのトークンは平文保存」「Ls ページネーション未実装」「Cd は権限不要」「Quota.file_count は 0 固定」は仕様上の妥協であり、設計書で解消する。
