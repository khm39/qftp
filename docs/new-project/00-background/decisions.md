# 決定事項(ADR ログ)

新規プロジェクトの設計を縛る決定を記録します。各項目は「状況 → 決定 → 理由 → 帰結」の順です。プロトタイプ時代の決定は必要なものだけ引き継ぎ、番号を振り直しています。

## ADR-001 ネイティブサーバ / クライアントの QUIC スタックは quiche、ランタイムは tokio(current_thread)

- **状況**: プロトタイプは quiche + mio(ネイティブ)と quinn + tokio(ブリッジ)の 2 系統を持っていた。新規プロジェクトの方針として quiche の採用が指定された。
- **決定**: ネイティブサーバとクライアントは quiche(BoringSSL)を使い、tokio の `current_thread` ランタイム上で駆動する。ソケットと全 quiche 接続を 1 タスクが持ち、タイマーは `tokio::time`、ファイル I/O は `spawn_blocking` / `tokio::fs`(ADR-005)。GSO は tokio の `UdpSocket` にないため `try_io` 経由で `sendmsg` を呼ぶ。
- **理由**: quiche は方針指定。加えて Cloudflare エッジでの運用実績。ランタイムに tokio を選ぶのは、quiche がソケットもタイマーも呼び出し側任せで mio でも tokio でも駆動でき、tokio なら自前の I/O ワーカープールと起床配管が不要になり、ブリッジ(wtransport、ADR-006)と同じランタイムになるため。`current_thread` を選ぶのは、単一タスクが全接続を持つ構造を保ち接続状態にロックを持ち込まないため(プロトタイプの mio ループと同じ性質)。当初案は mio + 自前ワーカープールだったが、2026-09-03 に tokio へ変更した。
- **帰結**: 転送処理を 1 タスクの中で扱うため、状態機械を明示的に書く必要がある(ADR-002 で純粋ロジック化)。ディスク I/O はブロッキングプールへ(ADR-005)。tokio の依存グラフとバイナリサイズはブリッジで既に受け入れているもの。マルチコアが必要になれば接続ごとのタスク分割(配送タスクが DCID で振り分け)へ移行できるが、その前に複数プロセス構成で足りる見込み。TOFU / ホスト名検証はハンドシェイク後に行うため、検証前にアプリケーションデータを送らない規律をクライアントコアで型により強制する。tokio-quiche(2026-09-03 時点で 0.19.1、MSRV 1.88、Cloudflare の `foundations` クレートに依存)は接続ごとタスクのマルチスレッド構造で配管が多く、MVP では採らない。マルチコアが必要になった時点で再評価する。

## ADR-002 転送エンジンは sans-I/O の状態機械として 1 実装

- **状況**: プロトタイプは転送状態を共有クレートに、遷移をサーバに置き、ブリッジは別実装を持っていた。
- **決定**: Get / Put のサーバ側・クライアント側状態機械を `qftp-core::transfer` に置き、入力はイベント(バイト到着、FIN、I/O 完了、送信余地)、出力はコマンド(ファイル読み書き、送信、応答、コミット、中断、会計)とする。エンジンはソケットにもディスクにも触れない。
- **理由**: quiche ループ、tokio ブリッジ、純メモリのテストが同一コードを駆動できる。失敗時の後始末規則を 1 箇所に集約できる。
- **帰結**: ホストごとにアダプタ(イベント供給・コマンド実行)が必要。エンジン API は転送エンジン機能設計書で固定する。

## ADR-003 ワイヤ符号化は手書き codec

- **状況**: プロトタイプは bincode 1.x(unmaintained)で仕様と同一バイト列を得ていたが、`#[serde(default)]` が無効であるなど誤解を招く構造だった。
- **決定**: `qftp-wire` に手書きのエンコーダ / デコーダを実装し、適合性はゴールデンベクタで担保する。serde は JSON 表現と設定ファイルのみに使う。
- **理由**: 仕様が bincode を非規範と明記している。末尾フィールド欠落の寛容デコードを残りバイト長で自然に実装できる。
- **帰結**: 約 500 行の codec と、ベクタに無い組合せを補う往復テスト・fuzz が必要。

## ADR-004 OS ユーザ分離は行わない(仮想ユーザモデル)

- **状況**: プロトタイプで setuid ワーカー方式を実装したのち却下した。
- **決定**: 単一の非特権プロセスで動作し、ユーザ単位の home と ACL はユーザ空間で強制する。
- **理由**: root 相当コンポーネントの追加はセキュリティ改善として割に合わない。qftp は OS アカウントを要求しない FTP 仮想ユーザモデルを志向する。
- **帰結**: カーネル DAC による多層防御はない。運用者は専用ユーザで起動し、root を限定する。

## ADR-005 ディスク I/O は tokio のブロッキングプールに委譲

- **状況**: プロトタイプは Get / Put のファイル読み書きをイベントループ上で行い、遅いディスクが全接続を止めた。
- **決定**: ファイルの open / read / write / rename / メタデータ操作は `tokio::task::spawn_blocking`(または `tokio::fs`)で実行し、完了は `JoinHandle` の await で受け取る。QUIC ドライバのタスクはソケットと状態遷移だけを扱う。プールの大きさは `limits.blocking_threads`(既定 CPU 数 × 2)。
- **理由**: HOL の解消。ADR-002 のコマンド / イベント方式と自然に整合する(エンジンの `Cmd::ReadFile` 等をホストが `spawn_blocking` に写し、完了を `Event::ReadDone` として戻す)。自前プールと起床配管を書かずに済む。
- **帰結**: タスク間往復のコスト。小さな要求では無視できる範囲と見込むが、Phase 3 の e2e で計測し、必要なら Stat 等の軽い操作はドライバタスク上で同期実行する。

## ADR-006 Web ブリッジは wtransport(quinn + tokio)の別バイナリとする

- **状況**: ブラウザには生の QUIC API がなく、WebTransport(HTTP/3 上の拡張 CONNECT + ストリーム振り分け)が唯一の経路である。quiche で終端できるかを 2026-09-03 に quiche master(`quiche` 0.29.3)のソースで調査した。
- **調査結果**:
  - 実装済み: 拡張 CONNECT の SETTINGS(`h3::Config::enable_extended_connect`、`extended_connect_enabled_by_peer`)、HTTP/3 datagram の SETTINGS。ヘッダはリストのまま渡されるため `:protocol: webtransport` の CONNECT 自体は受理・応答できる。
  - 未実装: WebTransport 固有の SETTINGS、双方向ストリーム先頭の信号値 `0x41` とセッション ID の解釈、セッションへの振り分け、capsule による終了。ソース中に該当箇所はない。
  - 外側から足せない: `h3/stream.rs` は「双方向ストリームはすべて request ストリーム」として先頭から HTTP/3 フレームとして解釈し、未知フレーム種別は「次の varint を長さとみなして読み飛ばす」。WebTransport ストリームでは `0x41` の直後がセッション ID のため誤解釈して壊れる。`h3::Connection::poll` は `conn.readable()` の全ストリームを処理し、特定ストリームを h3 管理から外す公開 API はない。
- **決定**: ブリッジは wtransport(quinn + tokio)を使う**別バイナリ** `qftp-web-bridge` とする。quiche 方針(ADR-001)の明示的な例外である。`qftp-core` の sans-I/O 転送エンジンを tokio ホストで駆動し、トークンスキーマ・origin ポリシーは `qftp-core` に置く。SPA の静的配信はブリッジの責務から外す(開発用の簡易配信のみ)。
- **理由**: プロトタイプで動作実績があり実装コストがほぼゼロ。代替の「quiche の生 QUIC 上に HTTP/3 最小サブセット(制御ストリーム、SETTINGS、静的テーブルのみの QPACK、拡張 CONNECT、WebTransport 振り分け)を自前実装する」案は 2,000〜3,000 行規模でブラウザ相互運用の検証負担が大きく、ブラウザ利用が主用途と判明するまで見送る。
- **帰結**: ワークスペースに quinn 系スタックが残り、ブリッジの MSRV が高くなる。サーバとブリッジのクォータ・使用量カウンタはプロセスごとに独立する(運用設計書に制約として記載)。ネイティブ側も tokio(ADR-001)のため、将来ブリッジを `qftp-server` の feature として同一プロセスに載せ、カウンタを共有する選択肢がある(quiche と quinn を 1 バイナリにリンクする代償と引き換え)。

## 引き継がない決定

- プロトタイプの「ブリッジのトークンは平文保存」「Ls ページネーション未実装」「Cd は権限不要」「Quota.file_count は 0 固定」は仕様上の妥協であり、設計書で解消する。
