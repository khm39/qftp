本書について

本書は qftp/1(QUIC 上のファイル転送プロトコル)を、図と表で読めるように解説したものです。正本は同じディレクトリの Markdown 仕様書(qftp-protocol.md、wire-format.md、error-codes.md、versioning.md)であり、本書と食い違う場合は正本が優先します。本書のバイト列の例はすべて test-vectors/ のゴールデンベクタを仕様どおりに復号して機械生成したもので、手書きの転記はありません。

凡例
  • BE ビッグエンディアン、LE リトルエンディアン。
  • 図中の C はクライアント、S はサーバです。実線は必ず送られるもの、破線は条件つきです。
  • 「実装定義」はワイヤが規定せず、各実装が自由に決めてよい値です。参照実装の値を参考として示します。
  • RFC 2119 の MUST / SHOULD / MAY は正本と同じ意味で使います。

全体像

qftp は FTP の「制御接続 + データ接続」を、1 本の QUIC コネクションに置き換えます。コマンドもファイル本体も、クライアントが開く双方向ストリームの上を流れます。

層内容
トランスポートUDP + QUIC v1(RFC 9000)。TLS 1.3 必須。mTLS は任意(設定時はクライアント証明書を強制)
バージョン交渉ALPN 識別子 qftp/1。不一致は QUIC ハンドシェイク失敗として現れ、プロトコル往復はゼロ
ストリームクライアント発の双方向ストリーム(ID 0, 4, 8, …)。先頭フレームは必ず Request、続いてサーバの Response(Get は複数)
本体Get / Put のファイル本体は制御フレームの直後、同じストリームに流れる(§9、§10)
接続の終わりQuit に Ok を返した後、サーバが CONNECTION_CLOSE を送る

設計上の要点: ストリーム間に順序がないため、コネクション状態である cwd(Cd)は「応答を受け取った後に出した要求」にしか保証されません(§8)。逐次実行しないクライアントは / 始まりの絶対パスを使うべきです。

コネクションのライフサイクル

局面規定
アドレス検証サーバは最初の Initial に stateless retry を要求してよい(MAY)。トークンはクライアントに不透明で、形式は実装定義(§13)
identitymTLS 時はハンドシェイク完了時点の peer 証明書から解決する。それ以前は anonymous としてしか実行できない(§12 の identity gate)
cwd接続受理時にユーザのルート。identity が昇格したら昇格後ユーザのルートにリセット。Cd 成功時のみ変化
アイドル参照実装は max_idle_timeout 30 秒、keepalive なし。ブリッジ(WebTransport)のみ 15 秒 keepalive
終了Quit → Ok → サーバから graceful な CONNECTION_CLOSE

フレーミングとエンディアン

すべての制御メッセージは長さプレフィクス付きフレームです。

相互運用で最も多い間違い: フレーム長プレフィクスだけがビッグエンディアンで、ペイロード内の整数(判別子、長さ、数値フィールド)はすべてリトルエンディアンです。
規則内容
上限長さプレフィクスが 16 MiB(0x0100_0000)を超えるフレームは、ペイロードを読まずに拒否する(MUST)。宣言された長さより大きいバッファを確保してはならない
消費受信側は必ず 4 + length バイトを消費する。それ以降のバイトは次のフレームか本体ストリーミング層に属する
フィールド上限フレーム上限だけでは個々の文字列や配列は抑えられないため、復号後にフィールド上限(§15)を適用する(SHOULD)
切り詰めペイロードの途中でフレームが終わる(フィールドが足りない)場合は Malformed

プリミティブ符号化

ペイロードは以下のプリミティブをタグも区切りも入れずに連結したものです。フィールド名はワイヤに載りません(位置依存)。

型符号化図
u8 / u16 / u32 / u641 / 2 / 4 / 8 バイト、LE
bool1 バイト。0x00=false、0x01=true。それ以外は拒否
Option<T>タグ 1 バイト。0x00=None(後続なし)、0x01=Some + T の符号化。それ以外は拒否
stringu64 LE のバイト長 n、続いて n バイトの UTF-8(NUL 終端なし)
seq<T>u64 LE の要素数 n、続いて T の符号化 × n
[u8; N]長さプレフィクスなしの N バイト
structフィールドを宣言順に連結。区切り・パディング・タグなし
位置依存 enum判別子 u32 LE(宣言順の 0 始まり)、続いてそのバリアントのフィールド。未知の判別子は復号不能 → Malformed。Request / Response / ErrorDetails が該当
数値 enumu32 LE の値(位置ではなく割り当て番号)。未知の値は Unknown(n) として保持し、フレームは拒否しない。ErrorCode / FileType / HashAlgorithm / Encoding が該当

トレーラは何をハッシュするか

トレーラは平文の累積範囲 [0, offset + 本体長) のダイジェストです。再開(offset > 0)では、サーバは自分のファイルから、クライアントはローカルの partial から [0, offset) を読み直して先に畳みます。したがって length 未指定ならトレーラはファイル全体のハッシュに等しく、サーバ側ファイルが同じサイズで中身だけ変わった場合(total_size では検出できない)も不一致として検出できます。これが「再開 Get で checksum_follows = false を禁止する」理由です。

検査違反時
offset > lenInvalidRange + Range { offset, file_size }
total_size < offset(再開中に縮小)InvalidRange
再開 Get に checksum_follows = false禁止(サーバは送ってはならない)
圧縮時に size != plaintext_sizeクライアントはプロトコルエラーとして扱う(SHOULD)
トレーラ不一致クライアントはデータを破棄する(MUST)

クライアントは accept_encoding に復号できるコーデックを優先順で並べ、サーバは対応するものを 1 つ選んで FileReady.encoding で答えます。小さいファイルや既圧縮ファイルでは Identity を選んでよい(MAY)。空の accept_encoding は Identity のみを意味します。

サーバの状態early data の扱い
mTLS 必須、または名前付きユーザが設定されているすべて拒否(許可リストの要求も)。early data は anonymous としてしか実行できず、昇格後のユーザとは別のトラストドメインだから
identity を持たない(全員 anonymous)ゲート 1 のみ

拒否は Unsupported(405)で返り、クライアントはハンドシェイク完了後にバックオフなしで即時再送します(MUST)。拒否の理由が 0-RTT であることだけで、操作自体は有効だからです。参照クライアントはチケット(ホストごと、0600、24 時間)を保存しますが、early data にアプリケーションデータは載せません。

stateless retry・レート制限・接続 ID

項目規定参照実装(実装定義)
retry最初の Initial に retry を要求してよい(MAY)。トークンは送信元アドレスと元の DCID にコミットする"qftp1" || 発行時刻 || IP || port || dcid_len || dcid || HMAC-SHA256[..32]、有効 60 秒(タグは 20 バイト以上)
接続レート制限Initial ごとに送信元 IP で検査。超過は黙って破棄トークンバケット 50 req/s、バースト 100
要求レート制限確立済み接続で Request 復号時に per-IP で検査。超過は RateLimited + RetryAfterInitial 用とは別のバケット群。同じく 50 req/s、バースト 100
サーバ接続 IDクライアントの DCID から決定的に導出する(SHOULD)。再送 Initial が同じ接続に収束するHMAC-SHA256(プロセス寿命の seed, client_dcid) を CID 長に切り詰め

バージョニングと拡張

メジャーバージョンは ALPN(qftp/1)で運びます。符号化は位置依存で自己記述ではないため、同一メジャー内で許される構造変更は既存メッセージの末尾へのフィールド追加だけです。

変更同一メジャー内で可能か備考
メッセージ末尾へのフィールド追加可(条件つき)旧デコーダは余剰バイトを無視できる。新デコーダは旧フレームを受けるために「短い形状 + 既定値」を明示的に受理し、既定値を文書化する(MUST)
数値 enum への値追加(ErrorCode 等)可(前方互換)旧側は Unknown(n) として読み進む。受信側が扱えない値は Unsupported で優雅に失敗
Request / Response / ErrorDetails のバリアント追加不可旧側は復号できない(Malformed)。新メジャーが必要
フィールドの並べ替え・削除・型幅変更、判別子の付け直し、エンディアン変更不可新メジャー(qftp/2)

いずれの変更も、ゴールデンベクタの追加と protocol-changelog.md への記録が必須です。qftp/2 に先送りされている方向(自己記述エンコーディング、varint、帯域内 capability 交渉、メッセージ層 MAC、Copy / Symlink / Transaction)は同ファイルにあります。
